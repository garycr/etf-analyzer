# Program Narrative

The specified/proposed ETF prototype is a local-first, single-user browser workbench for ETF research and hypothetical portfolio accounting. The source scope in the Objective PDF spans pages 1 through 14 and defines a product that is intentionally research-only, not a brokerage or execution system. It explicitly disallows a brokerage connector, real-order endpoint, credential transmission path, or any mechanism that would create a live trading capability. The system is designed to ingest prior-day ETF and economic data, run deterministic analytical rules, present evidence-bearing signals, and maintain a complete hypothetical ledger while preserving local provenance and explicit user confirmation.

The design is constrained from page 1 onward. The product mission is local, single-user, and browser-based; it does not include streaming or intraday feeds, advice or guarantees, real-money operations, paid-data dependencies, options/futures/leverage/margin/shorting/tax support, multi-tenancy, HA/DR, mobile support, Azure deployment, or backward-compatibility layering. On page 2 the explicit non-goals are clear: the prototype is not a brokerage system, not a real investment execution path, and not a general-purpose market-data platform. The meaning of UTC and the exchange calendar is part of the operating model; missing or unvalidated data blocks analytics rather than producing silent success. Provider policy artifacts and user settings acknowledgments must be maintained as explicit controls, not implicit assumptions.

The workbench includes watchlists, symbol validation, resumable backfill, and local provenance. Pages 3-4 define requirements for watchlist CRUD and reorder behavior, deduplication, fallback handling, raw and normalized data capture, idempotent ingestion, DQ checks, failure suppression, and generic economic series models with metadata and vintages. The objective also requires deterministic snapshot analytics and neutral labels for evidence, audit, and signal communication. It names specific functional groups: watchlists, market data, economics, analytics, criteria, backtesting, portfolios, UX, operations, AI constraints, and export controls. The design is intentionally bounded so research artifacts can be evaluated without creating an execution path or hidden brokerage semantics.

The architecture in pages 7-8 is a proposed target, not an accepted implementation. It calls for four deployables plus a shared PostgreSQL cluster: web API, portfolio service, ingestion worker, and analytics worker. The application is local-first and WSL-hosted Kubernetes is the principal deployment pattern, with readiness failures when migrations and database connectivity are unavailable. No load balancer or internet-facing listener is required by default. Paper-order state transitions remain deliberately local and must not rely on a provider-side paper-trading API; only the user may confirm a paper action. The ledger is the source of truth for fills, cash, lots, valuations, and performance, and it is derived from the same rules used in the research environment.

The data model and provider constraints are explicit. Pages 4-6 call out provider roles and quotas for yfinance, Alpha Vantage, Tiingo, Alpaca IEX, EODHD, Stooq, FRED/ALFRED, BLS, BEA, and Treasury Fiscal Data. These are not treated as permanent truths; all provider assessments require revalidation before use. The design requires direct official adapters for economic data, append-only vintages, and versioned transformations rather than overwriting observations. It also requires a product control that disables free organizational ingestion until rights are confirmed, plus a settings acknowledgment record that captures intended use, provider, terms URL/date, persistence/display permissions, and user choice. There is also a requirement to avoid failover within a dataset, to use fixtures when live sources are unavailable, and to keep local research separated from broader organizational use.

The system also defines explicit operational and UX requirements that are received as target quality gates rather than assumed completion criteria. Under page 10, the UI must support keyboard navigation, visible focus, semantic headings, labels, and non-color-only communication. The performance goals are concrete: p95 API response under 1 second for non-analytical requests, dashboard first meaningful content under 2 seconds, and the interface must be usable at 1280x720. Intelligence and AI are constrained to a future, clearly bounded role; the prototype is not a general autonomous trading or advice system. Exported files are user-owned but subject to provider policy, and redacted diagnostics must stay free of keys, passwords, prohibited raw provider payloads, and brokerage artifacts.

The legacy evidence remains secondary and is not a target-state mandate. The .NET and SQL Server historical implementation demonstrates how the prior workflow fetched symbol ranges, extracted HTML tables, and persisted records in a machine-bound data model. That evidence is valuable for migration mapping, risk identification, and understanding the initial assumptions, but it does not define the specified target architecture. The objective PDF is the authoritative boundary for scope, constraints, and acceptance criteria. The target design is therefore a proposed local-first prototype with explicit provider control, deterministic analytics, a paper ledger, and a migration path that preserves the lessons of the legacy system without inheriting its brittle assumptions.
